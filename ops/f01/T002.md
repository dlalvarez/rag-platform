Alcance aprobado: F01-R02 → AC-F01-01/02 parciales → P2 → T002 → V01/V02.
PR #9 aceptado e integrado en develop. T002 requiere su propia revisión humana.

## Ejecución

Desde la terminal SSH del operador y el checkout de la rama T002:

    python3 scripts/f01_host.py build tools
    python3 scripts/f01_host.py run --rm control-check
    python3 scripts/f01_host.py run --rm sql-check

El último comando exige terminal propia antes de contactar servicios o leer archivos.
Solicita la contraseña existente del operador OpenBao por entrada oculta. No usa root
de OpenBao, no solicita la clave de desbloqueo y no exporta credenciales. Si está sellado,
usar primero el comando unseal documentado; nunca init/resume para repetir pruebas.

La sesión del operador emite un SecretID de un uso. AppRole autentica por TLS,
los secretos SQL se generan en memoria y se guardan con CAS en KV versionado;
control guarda UUID/versiones. El token AppRole queda sujeto a su TTL y se descarta
al cerrar el proceso; el token operador se revoca al terminar. Sin archivos de tokens,
variables de entorno con passwords ni secretos en argumentos. No imprimir salidas
completas de Docker, SQL o OpenBao para diagnosticar fallos.

## Bootstrap y privilegios

El perfil sql-check monta exclusivamente las dos credenciales SQL de bootstrap/control
ya protegidas fuera de Git, además de la CA pública. La credencial superusuario SQL
solo prepara la plantilla/rol administrativo y una fixture de colisión NOLOGIN.
No confundir ese bootstrap SQL con el root de OpenBao, que sigue revocado.

La plantilla propia parte de template0 sin modificarla; vector queda en public con
versión y propietario verificados. No contiene tablas ni contenido de tenant.
Se revoca PUBLIC y se bloquean conexiones cuando finaliza el bootstrap.
El provisionador SQL tiene CREATEDB/CREATEROLE, sin SUPERUSER: estos permisos
son administrativos de clúster, no un sandbox. Su referencia está separada de las
credenciales app/migrator/readonly y su contraseña solo la consume esta CLI.

Por tenant: owner NOLOGIN; migrator puede SET ROLE únicamente a su owner.
App/readonly carecen de membresías, CREATE de esquema/BD y privilegios globales.
La BD nace ALLOW_CONNECTIONS=false; se aplican ACL explícitas antes de habilitarla.
Las reglas HBA impiden usar credenciales tenant en socket local y bases de sistema/control.
La recarga de HBA no reinicia PostgreSQL ni OpenBao.

El módulo provisioning/postgres usa UUID internos, identificadores psycopg citados,
parámetros para valores y verificadores SCRAM al establecer passwords.
Target recibe ubicación administrativa explícita; no acepta una URL de cliente.
El perfil de ensayo obtiene la instancia del catálogo y valida su asociación.

## Migraciones, reintento y límites

Control 0002 añade la referencia/version de readonly. Control 0003 amplía ssl_mode
de 10 a 11 caracteres para admitir el valor obligatorio verify-full. El par es nullable para preservar
registros T001; T002 exige ambos al crear ubicaciones nuevas. Constraints impiden
versiones no positivas y compartir el secreto con app/migrator. No hay backfill de
contraseñas ni downgrade destructivo.

Tenant 0001 crea únicamente ops_identity y alembic_version_tenant en public.
Sus permisos se retiran de app/readonly; no son tablas de negocio.
La pista usa conexión migrator explícita y owner propio. Los locks de migración,
canary, migraciones de fallo/reversibles y coordinación de versiones son T006.
El lock administrativo de la primitiva SQL serializa roles/CREATE DATABASE;
no acredita el journal ni la recuperación concurrente de T004.

Fixtures A/B usan UUID estables exclusivos del ensayo. Se conservan roles, bases,
referencias y credenciales al repetir; nunca se rota una contraseña para reparar
un secreto ausente. Los tenants permanecen PROVISIONING/NEEDS_MIGRATION,
sin observed_version ni READY hasta la coordinación y probes completos posteriores.
La tabla f01_synthetic_probe solo pertenece al ensayo; las pruebas CRUD revierten
sus cambios y no contienen documentos ni datos de negocio.

Los rechazos de conexión inicial pueden carecer de SQLSTATE en libpq.
El probe exige acceso propio positivo, CONNECT falso en ACL para el cruce SQL y
rechazo FATAL específico del destino. Para HBA exige firma de usuario/base/SSL.
No acepta errores de red, TLS o password. Mensajes ingleses del perfil fijado:
si cambian, el ensayo falla cerrado; no imprimir el error original para diagnosticarlo.

Se comprueba propiedad por comentario interno, owner, atributos, membresías y ACL.
Un nombre coincidente no autoriza adoptar un recurso. Una fixture NOLOGIN ajena
demuestra rechazo antes de crear la BD u otros roles; queda conservada.
La ventana CREATE DATABASE → comentario no es transaccional: si se interrumpe,
el siguiente intento se detiene para revisión, sin adoptar ni borrar la BD.
Reconciliación completa y compensación pertenecen a T004.

## Fallos y rollback

El comando imprime solo fase y código cerrado/SQLSTATE, nunca excepción/DSN.
No insistir ante un error de ownership o secreto ausente: conservar recursos,
revisar metadatos saneados y corregir mediante PR. No DROP DATABASE, limpieza
de buckets, reinicialización de Raft ni regeneración de credenciales.

Rollback de código mediante PR; conservar catálogo 0002, datos y KV. No ejecutar
downgrade. Antes de volver a una herramienta antigua, revisar compatibilidad.
La configuración HBA anterior se conserva fuera de Git; restaurarla requiere
revisión y recarga explícita, porque retiraría las restricciones adicionales.

T002 no acredita la fase: faltan buckets/S3, saga, pools, dos instancias y baterías
de migración. Ningún merge, despliegue de producción o cambio de visibilidad automático.
