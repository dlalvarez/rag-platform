## Acceso y comandos

Solo SSH de administración en ragdev01. No es identidad de usuario final, no implementa
AuthorizedTenantContext/OIDC de F02 y no hay endpoint público. Audit actor identifica
al operador diego autenticado por OpenBao; no crea una tabla de usuarios.

Desde el checkout operativo del servidor:

    python3 scripts/f01_host.py run --rm admin --help
    python3 scripts/f01_host.py run --rm admin-read show --instances
    python3 scripts/f01_host.py run --rm admin-read show --tenant UUID_TENANT
    python3 scripts/f01_host.py run --rm admin create --instance UUID_INSTANCE --key UUID_CLAVE
    python3 scripts/f01_host.py run --rm admin retry --tenant UUID_TENANT
    python3 scripts/f01_host.py run --rm admin-read check --tenant UUID_TENANT
    python3 scripts/f01_host.py run --rm admin-read migrate --tenant UUID_TENANT

Sustituir los UUID indicados por identificadores reales. show --instances devuelve los
destinos del catálogo; no se acepta host, BD, URL, contraseña o secreto en argumentos.
Una clave idempotente nueva es un UUID generado por el administrador; conservarla para
retomar la misma solicitud. No reutilizarla para pedir otro destino.

show requiere acceso SSH/archivos protegidos de control, sin sesión OpenBao; emite solo
metadatos explícitos de estado, destino, operación/pasos y pendientes. No valores de
secretos ni serialización completa del ORM. create/retry/check/migrate requieren TTY,
contraseña del operador OpenBao y políticas exactas. No usar root ni clave de desbloqueo
como contraseña. No redirigir/registrar entradas sensibles ni pegarlas en chat.
Parser rechaza valores inválidos sin reproducirlos en errores.

admin recibe solo control y administración IAM MinIO; los secretos SQL de provisionado y
tenant se leen por referencia desde OpenBao. admin-read recibe únicamente control:
check/migrate no requieren administrador IAM ni SQL bootstrap. OpenBao root sigue revocado.
Todas las conexiones verifican CA/nombre. No se copian secretos a checkouts ni argumentos.
Conservar una única herramienta activa a la vez: F01 con una herramienta suma 5 GiB.

## Qué hace cada comando

create reserva/reutiliza la clave, ejecuta la saga aprobada y devuelve metadatos seguros.
READY solo tras migración y probes. Repetir clave/destino devuelve la misma identidad,
sin duplicar recursos o rotar credenciales. Solo instancias ya registradas/aprobadas.
No registra proveedores ni realiza bootstrap nuevo por iniciativa propia.

retry busca la operación por tenant antes de actuar; desconocido no provoca alta.
Retoma la clave y referencias existentes. No adopta recursos sin marca ni restaura
secretos ausentes sobre recursos presentes. Las fixtures históricas T002 sin operación
no se convierten en tenants nuevos ni se promueven automáticamente.
Si provisioning ya SUCCEEDED pero falló una migración posterior, usar migrate; no
forzar create/retry para cambiar estado ni modificar el catálogo manualmente.

check exige READY/esquema compatible, operación SUCCEEDED y pasos completos. Lee
identidad, versión y vector reales con migrator bajo el lock, sin ejecutar DDL/Alembic.
Comprueba conexiones app/readonly con TLS y sin privilegios globales.
Hace put/get/list/delete de un objeto sintético único en _f01/admin-check y verifica
rechazo de GET anónimo. No usa administrador IAM ni modifica passwords/estados.
La limpieza se limita al objeto sintético escrito por esa comprobación. Una interrupción
puede dejar un objeto de prueba; no limpiar objetos de negocio ni borrar buckets.
Un fallo de check informa error; no repara secretos ni publica READY.
No sustituye las pruebas cruzadas ampliadas ya registradas en T006.

migrate aplica el coordinador aprobado de T006 sobre la ubicación del catálogo:
NullPool, lock por tenant en la misma conexión Alembic, versión/identidad comprobadas,
FAILED/MIGRATION_FAILED ante error y READY únicamente tras resultado verificado.
Solo operaciones de provisioning SUCCEEDED, tenant no suspendido y versión soportada.
Repetir es no-op de esquema. No downgrade canónico, stamp falso ni migración de datos
entre instancias. Sesiones ya prestadas no se revocan al cambiar estado.

## Diagnóstico y reversión

- INPUT_INVALID: consultar --help, usar UUID; no introducir secretos en opciones.
- UNKNOWN_TENANT/UNKNOWN_OPERATION: comprobar UUID con show; no crear sustitutos ni adoptar legacy.
- NOT_READY: show indica pasos/estado; recuperar con retry o migrate según origen.
- OWNERSHIP_CONFLICT o compensación REVIEW: conservar recursos y revisar atribución antes
  de otro intento. Nunca borrar recursos ajenos para conseguir un PASS.
- SECRET_* / F01-SEALED / F01-AUTH: revisar estado, custodia, autorización y referencias,
  sin mostrar cuerpos HTTP ni regenerar credenciales. No fallback a otro tenant/archivo.
- MIGRATION_FAILED: show, revisar versión/lock, corregir mediante PR y reintentar migrate.
  No forzar READY ni stamp.
- OPERATION_STOPPED: detener diagnóstico y conservar recursos. Revisar servicios, TLS,
  espacio y memoria sin publicar logs con secretos.

Rollback de código mediante PR revisado desde develop. No revierte por sí solo esquema
ni efectos externos; nunca reset destructivo de datos, DROP DATABASE o borrado de buckets.
Los binds conservan datos al detener servicios; no ejecutar stop/down como parte de una
prueba normal ni afectar F00. No se prueba aquí recuperación de datos de negocio.

Backup externo, restore, HA y PITR independiente no están acreditados. Antes de datos
relevantes se necesita backup consistente cifrado fuera de la VM y restore ensayado;
copiar archivos activos no constituye esa evidencia. MinIO upstream archivado conserva
el riesgo aceptado para desarrollo. Los secretos/CA deben protegerse también en backups.
No usar esta entrega como autorización de producción.
