## Flujo y recuperación

Una clave de idempotencia reserva un único tenant, operación y referencias versión 1.
Un lock de sesión por tenant excluye los efectos concurrentes. El journal usa transacciones
cortas; la conexión del lock permanece sin transacción durante HTTP/DDL externos.
Se revalida la propiedad en cada reintento, incluso si un paso anterior figuraba completo.
La misma clave con instancia, endpoint o versión incompatibles se rechaza.

RESERVE → SECRETS (CAS) → DATABASE → MIGRATE → STORAGE → PROBES → READY.
MIGRATE verifica identidad y revisión tenant 0001 reales antes de registrar la versión.
READY exige ese resultado y probes SQL/TLS/vector, S3 y referencias OpenBao correctos.
Esto no sustituye locks de migraciones generales, canary o dos instancias de T006.

Los recursos nuevos incluyen tenant y operación en comentarios SQL, tags de bucket y
marcadores de política. No se adoptan recursos heredados T002/T003 ni recursos sin marca.
Una caída tras CREATE DATABASE pero antes del comentario, o tras user_add antes del
vínculo IAM, puede exigir revisión manual; no se atribuye propiedad por nombre solamente.

Ante fallo se registra FAILED y el código cerrado, junto con recursos pendientes.
La compensación verifica propiedad antes de cambiar acceso: NOLOGIN y base sin nuevas
conexiones; usuario S3 propio deshabilitado. Conserva bases, buckets, datos y referencias.
Un reintento puede rehabilitar únicamente recursos de esa misma operación, sin cambiar
contraseñas. La compensación no termina conexiones SQL ya abiertas ni afirma invalidar
sesiones de aplicaciones futuras; los clientes de esta batería cierran sus conexiones.
Si falta propiedad o no responde un proveedor, queda REVIEW, nunca una limpieza asumida.

La revisión control 0004 añade estado de compensación y pendientes con códigos cerrados,
sin JSON ni campos de secretos. No tiene downgrade automático. Revertir código no revierte
efectos externos ni autoriza borrar recursos o aplicar revisiones anteriores.

## Batería V05

1. CreateBucket anónimo intencionalmente denegado por MinIO real. Tras fallo: SQL propio
   conservado y sin nuevos accesos, tenant FAILED. Reintento: mismo UUID, referencias,
   credenciales y OID SQL; finalmente READY.
2. Proceso hijo termina con código 86 después de SQL y antes de completar journal.
   RUNNING/PROVISIONING permanece; reintento reconcilia marcas y conserva identidades.
3. Dos procesos sobre una clave. El primero mantiene el lock; el segundo recibe LOCK_BUSY
   antes de incrementar intentos o ejecutar efectos. Tras liberar, existe una operación.
4. Bucket ajeno sintético con tags y canary diferentes. Rechazo OWNERSHIP_CONFLICT,
   contenido y tags intactos; pendientes REVIEW.

Los hijos reciben un SecretID de un uso mediante pipe anónimo, nunca argumentos,
variables de entorno o archivos. Cada hijo crea su cliente y conexión; ambos se ejecutan
dentro del mismo contenedor tools limitado. No hay agentes ni tareas de desarrollo paralelas.
