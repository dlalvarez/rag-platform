# T003: almacenamiento privado por tenant

F01-R04/R03 → AC-F01-03 parcial de fase → P3 → T003 → V03/V04.
Parte de T002 aceptada mediante PR #10 e integrada en develop.
Solo desarrollo y fixtures sintéticas; sin saga, resolver, usuarios finales o READY.

## Preparación y ejecución

Desde la terminal SSH y el checkout de la rama T003:

    python3 scripts/f01_host.py prepare-storage
    python3 scripts/f01_host.py up -d --no-deps minio
    python3 scripts/f01_host.py build tools
    python3 scripts/f01_host.py run --rm s3-check

prepare-storage es de una sola ejecución: rechaza cualquier preparación existente
o parcial, nunca regenera credenciales/certificados para reparar errores. Añade
solo el directorio MinIO F01, certificado minio firmado por la CA existente y dos
archivos administrativos protegidos fuera de Git. No modifica certificados SQL/Bao.
No ejecutar prepare de T001 sobre el entorno existente.

El launcher comprueba montaje/recursos, rutas sin symlinks y propietario/permisos
privados de claves y bootstrap. MinIO se ejecuta con UID/GID del operador, límites
de CPU/memoria, sin capacidades adicionales, puertos publicados o consola web.
Solo arrancar minio con --no-deps; no reiniciar OpenBao ni F00.

s3-check requiere terminal propia y contraseña existente del operador OpenBao.
No solicita unseal/root, no exporta secretos ni los pasa como argumentos/variables.
Si Bao está sellado, seguir unseal del runbook; nunca init/resume.
AppRole consume SecretID de un uso; la sesión del operador se revoca al terminar.
El token AppRole queda sujeto a TTL y se descarta al cerrar el proceso.

## Credenciales y políticas

La credencial administrativa MinIO es bootstrap del servicio y CLI, separada de
F00, SQL y los usuarios tenant. Sus archivos 0600 se montan solo en el servicio
MinIO y perfiles s3-compat/s3-check. No es el root de OpenBao: este sigue revocado.
Las pruebas de aislamiento usan credenciales propias, nunca ese administrador.

El SDK minio==7.2.20 ya estaba fijado en F00; se mueve de dev a runtime, sin cambios
de versiones/hashes de paquetes. MinioAdmin usa HTTP nativo firmado y cuerpo cifrado
para crear usuarios, sin ejecutar mc ni pasar passwords por línea de comandos.

Por tenant UUID: bucket rag-t-<uuidhex>, usuario/política f01-t-<uuidhex>.
Solo ListBucket en el bucket y GetObject/PutObject/DeleteObject en sus objetos.
Sin comodines globales, IAM/admin, grupos adicionales, política pública ni acceso
a buckets ajenos. El SDK fija región para no requerir GetBucketLocation adicional.

La referencia/version se reserva en storage_locations, junto al endpoint HTTPS
administrativo explícito. SecretStore conserva las credenciales versionadas con CAS.
En reintentos se leen las versiones existentes; recurso existente con secreto
ausente falla, sin regenerarlo. No hay nuevos campos ni migraciones de esquema.

## Propiedad y repetición

Antes de escribir: inspeccionar tags del bucket (tenant, ref opaca, contrato),
política exacta con tenant/ref en Sid, usuario habilitado con solo esa política y
sin grupos; rechazar cualquier política de bucket. Nombre coincidente no basta.
Un recurso desconocido no se adopta, modifica ni borra.

La creación guarda credencial antes del efecto externo; bucket privado/tags,
política y usuario/attach se verifican después. Repetir no hace user_add sobre
un usuario existente ni cambia password. La ventana bucket→tags o user→attach
puede dejar un recurso sin prueba suficiente de propiedad; se conserva y detiene
para revisión. Reconciliación, locks de saga, compensación y journal son T004.

No DROP/borrado de buckets ni limpieza automática de objetos ajenos. Las pruebas
solo eliminan su objeto propio temporal de delete; conservan canaries y fixture
ajena para comprobar que los rechazos no la alteraron.

## Pruebas reales y límites

s3-check usa los mismos A/B de T002, con secretos OpenBao y ubicaciones en control.
Comprueba put/get/list/delete propios; get/put/list/delete cruzados y get/put/list
anónimos denegados; API administrativa global denegada; fixture ajena intacta.
Solo AccessDenied cuenta como rechazo S3: una firma inválida, red caída o NoSuchKey
no acreditan aislamiento.

En esta release ListBuckets puede devolver la lista filtrada por ListBucket del
bucket propio, aunque no se conceda ListAllMyBuckets. La prueba exige exactamente
el bucket propio, nunca la lista de otro tenant. Ver fuente de la release:
[handler ListBuckets](https://github.com/minio/minio/blob/RELEASE.2025-10-15T17-29-55Z/cmd/bucket-handlers.go).

La calibración técnica opcional se ejecuta con:

    python3 scripts/f01_host.py run --rm -T s3-compat

Crea fixtures con UUID nuevos, fuera del catálogo tenant. Sus credenciales se generan
solo en memoria para este ensayo y los usuarios atribuidos se deshabilitan al terminar.
No usa un SecretStore alternativo ni sustituye la batería final con OpenBao.
Buckets/políticas/canaries sintéticos se conservan; no repetir sin necesidad porque
cada calibración añade fixtures. Si una creación parcial no acredita propiedad,
revisar antes de cualquier limpieza. No ejecutar calibración como provisioning tenant.

TLS verifica CA en clientes S3/Admin y healthcheck. Se probó además rechazo de CA
ajena sin fallback. CA/certificados de desarrollo tienen caducidad y renovación manual;
no se acredita producción, HA, backup externo o restauración. El upstream archivado
y la receta compilada de F00 mantienen su riesgo de mantenimiento; no se cambia proveedor.

referencias de control y KV. No rotar secretos ni volver a prepare-storage.
No retirar permisos a un recurso ajeno ni habilitar usuarios de calibración.

bucket público, documentos reales, API de alta ni cierre de F01. T004 solo después
